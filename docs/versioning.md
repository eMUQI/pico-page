# 版本管理

产品版本的唯一来源为 `firmware/version.txt`。`0.2.0-beta.1` 于 2026-10-12、`0.2.0-beta.2` 于 2026-10-13、`0.2.0-beta.3` 和 `0.2.0-beta.4` 于 2026-10-14 作为预发布发布。`firmware/version.txt` 现为 `0.2.0-beta.5`，本版处于发布准备阶段，尚未创建标签或发布；发布范围见[发布说明](releases/0.2.0-beta.5.md)，验证与待办见[开发状态](development-status.md)。历史标签 `v0.1.0-mvp` 保留，不重新编号。

## 编号与兼容性

采用 [SemVer 2.0.0](https://semver.org/lang/zh-CN/) 的三段编号和预发布排序，项目接受 `X.Y.Z`、`X.Y.Z-beta.N` 和 `X.Y.Z-rc.N`。三段数字不补零，阶段序号从 1 开始。

| 版本 | 用途 |
|---|---|
| `0.2.0-beta.N` | 同一轮测试的连续构建，允许调整功能 |
| `0.2.0-rc.1` | 功能冻结后的候选版，只修复发布阻塞问题 |
| `0.2.0` | 这一轮测试通过的发布版，项目整体仍处于 0.x 阶段 |
| `0.2.1` | 兼容的问题修复 |
| `0.3.0-beta.1` | 下一轮功能测试 |
| `1.0.0` | 首版范围与兼容性承诺稳定 |

0.x 阶段，兼容修复增加修订号，新增功能或不兼容调整增加次版本号。1.0 以后，兼容修复增加修订号，兼容功能增加次版本号，不兼容修改增加主版本号；高位增加时低位归零。兼容性重点包括 TF 卡配置、阅读进度和同步约定，内部重构不自动构成大版本。数据 schema 独立维护，不能用产品版本代替文件格式检查。

同一目标版本按 `beta.1 < beta.2 < rc.1 < 无后缀版本` 排序。每次发给测试者的新固件都增加版本号，已发布的标签与固件不可覆盖。发布说明面向读者，会显示在设备和网站的更新日志页上：写这一版新增和修复了什么，以及读者需要做的事（例如需要重新安装、需要迁移数据）。有不兼容调整或迁移要求时必须写明，并用读者能看懂的话说明后果，不写内部的格式版本号；没有时不写「兼容性」一节。已知问题不写进发布说明（2026-10-13 用户确认），记录在 Issue 和[开发状态](development-status.md)中。

1.0 的门槛是首版范围与相关验收完成，包括 EPUB 离线阅读、KOReader 双向位置接续和关键保存路径；不要求完成全部路线图。版本号本身不是验收证据。

## 构建与显示

固件和 host 共用 `tools/project_version.py` 解析版本；固件把结果写入 ESP-IDF 的 `PROJECT_VER`，设置页和使用说明通过应用描述读取同一版本。host 预览也显示该版本。

干净检出且 HEAD 带有匹配的 `v<版本>` 标签时，版本为文件中的原值，例如 `0.2.0-beta.1`。其余构建附加 `+g<七位提交号>`，存在已跟踪或未忽略的未跟踪改动时再附加 `.dirty`，例如 `0.2.0-beta.1+g1234567.dirty`。完整提交号和源内容摘要保存在构建来源记录中。源码必须来自 Git 检出，不从缺失的 Git 信息推断发布身份。

ESP-IDF 应用描述的版本字段为 32 字节，其中一字节用于终止符；脚本拒绝超过 31 字节的结果，不允许静默截断。不得通过 `PROJECT_VER` 缓存变量、Kconfig 版本覆盖或排除版本字段来绕过版本文件。

标准固件入口 `sh tools/build_firmware.sh [release|performance|diagnostic]` 每次重新配置以刷新 Git 状态，并在完成时检查镜像内版本。直接使用 IDF 时执行 `idf.py -C firmware reconfigure build`；host 执行 `cmake -S . -B build/host -DCMAKE_BUILD_TYPE=Debug` 后再构建。仅执行底层增量构建命令可能保留上一次配置时的 Git 标识。

`beta` / `rc` 表示发布阶段，`release` / `performance` / `diagnostic` 表示编译配置。普通测试者使用 `release` 配置，需要排障时才提供标明配置的其他产物。`provenance.json` 保留版本、构建模式、完整 commit、dirty 状态、来源摘要和产物 SHA-256；`default` 表示无参数构建入口，不能冒充 release 配置。

## 发布前检查

以下是获得发布授权后的操作约定。各版本的发布说明保存在 `docs/releases/<版本>.md`。

1. 修改 `firmware/version.txt`，更新本轮发布说明 `docs/releases/<版本>.md`，写法见上文；验证结果和已知问题记录在开发状态中。
2. 完成约定检查并提交本轮内容。发布来源必须是干净检出，Git 标签使用 `v<版本>`；不得移动已发布标签。
3. 在候选标签检出上执行 `python3 tools/project_version.py --check-release`。该命令只检查，不创建标签、不发布；缺少匹配标签、存在其他不匹配的 v 前缀标签或工作区有改动时拒绝。
4. 构建 `release` 配置，核对应用版本与来源记录，完成本轮要求的设备验证。打包时使用 `pico-page-<版本>-read_pico-<配置>.bin` 命名应用镜像，并附带对应 `provenance.json`、发布说明和适用许可。应用镜像用于联网更新，不是全量镜像，不能从 `0x0` 写入。全量镜像命名为 `pico-page-<版本>-read_pico-release-full.bin`，含 bootloader、分区表和同一个应用，用于擦除整片闪存后的首次安装（[决定](decisions.md) D41）。
5. 发布前再次执行标签检查，确认产物属于该提交且未被替换。Beta 和 RC 标为预发布；发布动作须单独获得授权。

不设置独立流水号，不引入自动发版服务。

## 联网更新使用的版本信息

设备端的版本比较在 `firmware/components/reader_sync/update.cpp`，与 `tools/project_version.py` 接受同一组版本形式：`+` 后的构建元数据不参与排序；带构建元数据的版本视为开发构建，不能据此判断新旧。清单中的版本必须是不带构建元数据的发布版本，并与镜像应用描述中的版本一致，否则设备拒绝写入。

更新清单由 `python3 tools/ota_manifest.py --image <release 构建的 pico_page.bin> --notes <发布说明.md> --out <目录>` 生成（`--out` 可以是任意目录，例如 `build/release`）。清单和镜像作为该版本 GitHub Release 的附件发布，不提交到仓库；网站构建工作流取回版本最高的发布，用同一脚本的 `--check` 核对后放进网站产物。步骤见 [网站说明](../web/README.md) 的「固件更新文件」。脚本先按 ESP 镜像格式校验整个文件（各段长度、校验和与末尾的 SHA-256），再从镜像读取版本，拒绝截断或损坏的镜像、开发构建、其他项目或芯片的镜像、超过 4 MiB 的镜像和超过 8 KiB 的发布说明，并按上文的命名复制镜像。加上 `--full` 时，脚本从同一个构建目录读取 `bootloader/bootloader.bin` 和 `partition_table/partition-table.bin`，合并出全量镜像；`--check` 在目录中有全量镜像时核对它的 bootloader、分区表，以及其中的应用与清单描述的应用镜像逐字节相同。每个版本同时发布全量镜像和应用镜像（D41）。脚本和网站也接受只有应用镜像的发布，此时设备可以联网更新，网站安装页不开放。清单的 `data_schema` 取自设备源码中的 `progress_schema` 和 `config_schema`；修改进度或配置文件格式时同步修改这两个常量。脚本不上传文件，发布到网站需单独授权。
