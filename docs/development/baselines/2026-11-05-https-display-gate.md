# HTTPS 与显示门控复测

2026-11-05 在同一台 Read Pico、同一张 TF 卡和原有 Wi-Fi／同步账户上复测 [#49](https://github.com/eMUQI/pico-page/issues/49)。后续已重新触发旧 `empty` 欠载，并定位到双供数任务的启动竞态；本地候选加入相位启动屏障。现有 HTTPS 门控在采样路径中生效，但不阻止 Wi-Fi 后台调度，不能据此前首批未复现而关闭 issue。本次交付以 #49 原报告的 `empty` 欠载为范围；独立的单次 `short` 短扫保留测量记录，不作为该 issue 的新增关闭条件。以下区分首批门控验证与后续复现、修复和复验。

## 首批来源与方法

未修改源码的 Diagnostic 来自 `a9820bd252f1bbc4d02999d494cbd8f9fafd70b0`，镜像为 4,074,944 字节，SHA-256 为 `c731211321fb0162138580fa82d1b61fa4ef1af4dee716c8dedd7b3c5bf918ee`。ESP32-S3 使用已有 EIM ESP-IDF 6.1，SDK 为 `fff9895c82d744c7237be8847347bdd1b07c6643`，保留本机 `ld.ext_ram.sections` 修改；BSP 为固定的 `5f3406deec33304de8801046db583dec7c49e55b`。生效配置为 16 MiB Flash、八线 80 MHz PSRAM、PSRAM TLS 分配及完整诊断事件。

设备报告 TF 为 SDABC、容量 29,818 MB，通过 USB 供电。测试书位于独立目录，均为合成 EPUB。小图书来自现有 `image-flow.epub`，SHA-256 为 `977a09f4d77f5ff6e7f4c4e7952badf42660a598997a5f06de1b6eface22277a`；大图书包含 1536 × 1536 灰阶 PNG，EPUB 为 1,828,307 字节，SHA-256 为 `247d55c506f726208fd80a467cc3ddc106a42fc210677bc93684d699b9deb595`。每本书首次打开使用新的书籍身份，后续取消轮次保留热页缓存；没有清除用户缓存。结果不能扩展为冷／热性能比较或完整图片解码专项。

两组取消样本均先完成一次只读远端位置检查，再通过正常界面等待 HTTPS 阶段、取消并尝试「继续离线阅读」，回正文核对原锚点、保存修订和字号，随后执行 K2。请求先结束而自动返回同步页的轮次单独记录。私有脚本复用现有工作台的串口、输入、事件和画布入口，每轮冻结并排空记录器，保留原始字节。测试不上传位置、不采用远端位置。

另以临时 Diagnostic 在 `http_step()` 每次取得网络侧门控后、SDK 返回前后读取单调微秒时钟，释放门控后输出序号与起止时间。探针增加固定 4 字节原子计数和固定局部量，没有新增任务、画布或动态缓冲。日志会改变调度和耗时，因此只用于观察调用互斥，不用于性能结论。探针镜像为 4,076,464 字节，补丁、源码快照和构建来源仅留在本机，测量后逐字恢复源码。

| --- | ---: | ---: | ---: | --- |
| 未修改源码、小图书 | 8/8 | 1/8 | 60，最终均成功 | `empty=0`；一次 `short=1`，重画成功 |
| 临时计时、大图书 | 8/8 | 0/8 | 61，均成功 | 未见欠载或恢复日志 |
| 临时计时、账户草稿真实超时 | 不取消 | 不适用 | 14，均成功 | 未见欠载或恢复日志 |

16 次取消均保留各自书籍的锚点、保存修订和字号，后续 16 次 K2 均确认完整全刷。只有第一组第 2 轮实际走完「继续离线阅读」；该轮正文呈现在 HTTPS 包装阶段结束约 132 ms 后开始。其余轮次没有覆盖这条完整路径，不能把工作台的不可判定结果改成整场景通过。最初脚本误要求诊断 tap 产生实体 `Input` 事件，原始结果保留为不可判定；后续以已收到 HTTPS 开始事件、接受的取消命令以及同一 HTTPS／Network 的取消终态重判，未补造设备点击时间。

第二组记录的 SDK 序号 1–198 连续，与全部 61 个呈现事务的设备单调时间区间逐一比较，没有交集。`NetworkStage` 与部分帧仍有交集，因为它包含门控等待和清理。源码中的 `http_step()` 与运行时显示准入共用原子状态，覆盖握手、发送、响应头、读取和清理；采样结果支持该门控在当前路径生效。它不停止 Wi-Fi／lwIP 的后台活动或中断，不能据此排除全部硬件竞争。

真实超时使用本机停滞 TCP 端点。设备只在账户草稿中临时填写私有局域网地址，端点收到两次 TLS ClientHello 后不回应，不提供证书或 HTTP。设备两次记录 `HTTPS connection failed: result=ESP_ERR_TIMEOUT`，HTTPS 包装阶段约 20.277 秒，随后自然失败。账户页 K2、退出草稿后重开原账户表单的画布 CRC、回原书的锚点／修订及阅读页 K2 均通过。未保存草稿，没有关闭证书校验。此项为一次异常恢复样本，不代表严格墙钟上限或全部故障矩阵。

三个采集窗口组的结构化事件均无缺口、溢出或未完成操作。超时窗口的 SDK 序号应有 3,216 条，只收到 3,193 条，缺少 23 条尽力输出日志。因此该窗口只认定超时、应用状态和驱动结果，不将已记录区间无交集当作完整 SDK 互斥证明。SDK 互斥结论使用上一组序号连续的 198 条记录。

## 剩余短扫

第一组第 6 次取消的「正在结束同步」呈现记录为 Overlay、Frame 48。原始诊断为 `invalid=0 empty=0 short=1 first_empty=-1 phase=35 consumed=684 total=688 prepared=690`，随后一次完整清屏重画成功。最终 Frame 成功会包含这次恢复，不能只看终态而忽略它。

固定 BSP 在 VSYNC 完成时发现 `lines_consumed < lines_total` 就将其归为短扫；本次不是队列读取为空。原生高度 684 向 8 对齐为 688，差值恰为一个四行 bounce buffer。`prepared=690` 是两个生产者领取行号并退出后的计数，不表示已经完成 690 行。现有证据不能判断是末尾 GDMA EOF 晚于 VSYNC，还是更早的 EOF 延迟或合并造成补写序号落后，也不能断言只是无害的填充行误报。

后续应在固定容量记录中保留尾部 GDMA EOF 的实际 descriptor 地址、回调计数、消费行数、VSYNC 状态和队列索引，再区分候选。未修改波形、扫描时序、任务优先级、队列容量或短扫判定。本轮没有面板光学观察、实体输入或长期运行证据。

## 首批检查与恢复

既有 `display_network_gate` 通过 host Debug 和独立 ASan／UBSan 检查；工作台原有 35 项 Python 测试通过。当前诊断版和临时计时版均通过固件构建及来源／产物摘要核对。这里没有运行完整 host CTest 或声称 LSan 通过。文档交接与差异检查另见开发状态。

刷写前实测分区和 otadata，完整备份原活动 `ota_1`，验证原镜像校验与摘要；仅写同一应用槽。结束后恢复原 `0.5.1+ga2871cc`，独立校验整个应用槽，核对分区元数据和 OTA 选择未变，并读回启动、出厂 VCOM 加载及 TF 挂载。测试书留在独立目录，本机停滞端点已关闭。完整备份、账户画布、私有服务信息及原始日志仅保存在忽略目录 `.local/verification/issue49-current/`。


## 后续复现与本地修复

继续追查时，先在无网络操作下完成 100 次 K2 全刷、100 轮工具面板开关（200 个呈现事务），再在保持 STA 连接、没有 HTTPS 的条件下完成 100 轮工具面板开关（200 个呈现事务）。这些对照均没有欠载、恢复或事件缺口；它们不是网络冲突场景的通过证明。

成功检查后保持 STA 连接，再取消 HTTPS，第 9 轮重新出现 `invalid=0 empty=638 short=0 first_empty=50 phase=15 consumed=688 total=688 prepared=52`。一次清屏重画恢复。随后在一次仅连接 Wi-Fi、没有 HTTPS 请求的正常界面路径中，出现 `empty=637 first_empty=51 phase=5`。两组均保留完整 172 次 GDMA EOF、稳定尾部快照和无 descriptor 失配记录；因此不能继续仅凭 HTTPS SDK 门控或尾部 DMA 候选解释旧故障。`prepared` 是领取行号数，空行累计也包含错误后停止生产造成的连锁，不代表每个计数都是独立调度失败。

第二组的生产者入口探针显示：第 32 行启动及首次 empty 时，只有 worker 1 已进入当前相位（`started_mask=2`）；父任务的第一次通知尚未返回，worker 0 尚未进入。worker 0 的同核入口时间比首次 empty 晚 378,658 CPU cycles，按 240 MHz 折算为 1.5777 ms。现有代码先通知另一核，再通知当前核；另一核可以独自达到预填阈值并开扫。证据支持这个启动竞态，没有测出究竟是哪一个 Wi-Fi 任务或中断延迟了父任务，也不据此排除其他中途停顿。

候选通过 `firmware/board/patches/epdiy-feed-start.patch` 修改固定 BSP 的构建副本：每个 `lcd_calculate_frame()` 在生产行及任何错误早退前，用静态 `xEventGroupSync()` 等待两个供数任务到齐。沿用原来的第 32 行唯一开扫条件和父任务每相位等待两个 `feed_done` 的交还条件；SDK 自动清除汇合位，不增加跨相位状态协议。单生产者清屏入口不进入屏障，原欠载检测、停止生产、队列清理和一次完整重画仍保留。

未改变 32 行预填、64 槽队列、任务优先级、波形、时钟、供电窗口或网络门控。新增等待发生在扫描前，生命周期仍依赖原有两个供数任务完成，不建立严格墙钟上限。新增的静态事件组为 36 字节，加 4 字节 handle；目标 map 的 `render_context` 从 `0xe8` 到 `0x110`，固定增加 40 字节，没有新增任务或堆缓冲。供数任务栈的新增峰值未单独测量，不能把静态对象大小当作整条调用路径的峰值。

### 候选验证

另在启动空白画面的两次通知间，分别插入一次 5 ms、20 ms 延迟。旧版均未欠载，单生产者在该画面足以供数；不能将其称为故障前后对照。20 ms 样本的旧版为 mask2 开扫，屏障候选为 mask3 开扫，均完整完成相位，仅作为启动准入改变的协议观测。真正的故障基线使用上面的自然 STA 建连与 HTTPS 取消日志。

| --- | --- |
| 临时固定容量探针、正常 STA 建连 | 新地址及后续页面呈现确认，回原书，未见欠载／恢复；没有 HTTPS 事件 |
| 同一候选、24 次已确认 HTTPS 取消 | 183 个呈现事务最终成功；24 次回正文及 K2 全刷保持锚点、修订和字号；无欠载、恢复或事件缺口 |

### 构建、检查与恢复

实际源码为 `a9820bd` 加本地补丁，沿用前述 IDF／BSP 及本机 SDK 链接脚本修改。最终无探针 Diagnostic 为 4,075,376 字节，SHA-256 `30ae11b8ac5be9c8c032dd35fedfc9937b3cf2884933428a7820c15f7eda4629`，相对同模式基线增加 432 字节，距 4 MiB 槽上限尚余 118,928 字节。Release 为 4,027,760 字节，SHA-256 `1db97801f29ddb47cda574908e22ee5729aaedc4fbfedc9af450449262f23e71`，尚余 166,544 字节。两种实际配置均启用静态分配，构建副本中没有临时探针或延迟；Release 仅构建，设备复验使用 Diagnostic。

完整 host Debug 与 ASan／UBSan 各通过实际注册的 35 项 CTest，包含 Node 页面测试和既有工作台测试；BSP FreeRTOS 屏障本身由目标构建与上述设备路径验证。原 CMake 的可选 BSP 波形测试未启用，没有把注册数量误写成历史的 36 项。AppleClang 21 明确报告不支持 `detect_leaks=1`，未声称 LSan 通过。独立源码审查未发现屏障代次、早退、静态对象生命周期或单生产者清屏的阻塞问题。

一轮烧录后的 stub 元数据读取中断，写入摘要已经通过；使用 ROM 回退独立比对分区元数据、OTA 选择及应用摘要，随后重新开始设备场景，没有将串口采集缺口拼接成连续通过。所有设备镜像仅写实测活动 `ota_1`。结束后完整恢复原 `0.5.1+ga2871cc` 应用槽，独立校验全槽摘要，分区及 OTA 元数据逐字相同，启动版本、出厂 VCOM 加载和 TF 挂载均确认。测试合成书和缓存留在独立目录；正常建连可能更新 TF 上的连接记录，未编辑账户凭据，没有改写工厂校准。

临时补丁与探针均已从交付源码移除，原始串口、构建来源、完整备份及私有账户画布仅留在忽略目录 `.local/verification/issue49-followup/` 与首批目录。修复通过 PR 交付，合入与发布另行执行。完整离线路径、独立短扫、面板光学、实体输入、长期运行及实际 KOReader 双向位置接续仍属于各自专项，不作为本次 #49 修复的新增关闭条件。
