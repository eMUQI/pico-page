# 2026-11-04 · 0.5.1 与主线实机性能对照

## 结论

本报告所说的「正文跨章翻页」是阅读正文时翻到上一章或下一章的操作，不包含目录列表翻页。本轮常规翻页中位数接近，未观察到整体提速；开书中位数在本轮比 0.5.1 高约 1.6%–4.6%，每组仅 5 个样本，不能据此认定稳定退化。在章节较多的书中，两版都出现过正文翻到上一章或下一章时等待数秒的情况：0.5.1 最长 4.857 秒，最新最长 5.232 秒。最新两轮的首个 300 章跨章请求均未命中相邻章节预取，约 1.04／1.06 秒；旧版对应样本命中预取，约 0.65 秒。预取调度差异和数秒等待的原因尚未定位，不关闭 Issue #104，也不据此宣称 PR #185 已改善所有跨章性能。

完整统计见[结构化结果](2026-11-04-v051-main-performance.json)。本批仅做测试、构建、应用槽安装及文档记录，没有修改生产代码或发布固件。测试完成后，用户授权将本报告和结构化结果提交至 `main` 并推送。

## 来源与条件

- 旧版采用干净 Diagnostic `0.5.1+g2b0e98d`，源码 `2b0e98d`；与正式 `v0.5.1/fed9891` 只有文档差异。最新采用本轮构建的干净 Diagnostic `0.5.1+g6429f79`；与已合并 `a2871cc` 只有文档差异。比较对象是正式版与主线各自同代码的诊断构建，没有把关闭诊断的正式 Release 当成已采集遥测的镜像。
- 两边生效 sdkconfig 键值完全一致；ESP-IDF 6.1 `fff9895c`、BSP `5f3406de`、Xtensa GCC 15.2.0、240 MHz CPU、80 MHz PSRAM、5 秒 watchdog 与双核 idle 检查保持。复用已有 EIM 工具链和 SDK 本地差异。旧版／最新应用为 3,987,760／3,992,096 B，4 MiB 槽余量为 206,544／202,208 B。旧版镜像、ELF、配置及 provenance 在构建前归档；本轮没有重建旧版、重跑 host／sanitizer 或远端 CI。
- 同一 RP-A 设备、同一 TF 卡和 USB 供电，未换卡；本轮未重新采集 TF 型号和文件系统。三个原创 EPUB 为 300 章、3000 章及 6 个多页章节，放入新目录 `Books/VersionPerf-20261104/`。内容 SHA-256 在 JSON 中，上传和每轮测试均核对设备长度／CRC32；原书未覆盖。
- 三书均使用 38 px，单书设置和全局其他设置在两版间保留。每书先开一次准备，再计 5 次重开、30 次前翻及 30 次回翻；起点和每次往返的已保存源锚点均核对。刷新配置未改，数值未从 TF 单独导出；两版都在每书前翻索引 20、回翻索引 11 记录到自动全刷，实际帧类型分组一致。
- 顺序为最新初轮、0.5.1、最新复测，每轮 195 个目标帧。初轮用于验证和完整路径磁盘预热；最终配对表使用后两轮，共 30 次重开及 360 次翻页。初轮另保留 15 次重开及 180 次翻页；不计入最终配对分布。没有清空磁盘缓存，不宣称冷路径；异步预取命中和后台状态按每步实际值保留，没有人为锁定。
- 计时从主机单调时钟发送串口动作前，到收到目标正文帧完成通知；计时区间不轮询 status。包含串口与调度开销，属于动作至驱动完成，不是实体触摸或光学响应。目标帧逐一匹配设备 Frame trace 的开始／结束，三个完整轮次的 585 个目标帧均有匹配。用 `tools/summarize_reader_perf.py` 汇总全部派生样本，`min_us=0`，保留全部慢样本；显示与其他准备时间不相加冒充纯 CPU 时间。

## 正文跨章等待与证据边界

0.5.1 的 3000 章回翻第 2 次请求为 4856.805 ms；对应 Chapter 任务为 4153.986 ms，目标帧 present 为 564.735 ms。最新复测的 3000 章首个前翻为 5232.030 ms；日志先结束一个已取消的章节任务，再执行 Chapter 任务 4382.789 ms，目标帧 present 为 537.211 ms。Chapter 墙钟包含 I/O、等待、调度和内部阶段，不能视为纯解析 CPU；中途的等待提示帧与 Chapter 并行，不能再次相加。两次均成功呈现，这两次等待都有完整计时记录，未将脚本超时计入其中。

最新初轮与复测的首个 300 章前翻分别为 1043.452／1057.088 ms，旧版为 649.737 ms。对应旧版的 `chapter_prefetch_hits` 增加，最新两轮均未增加，且请求前 `cache_chapter=0`、`cache_stream=0`；这是观测到的准备状态差异，尚未证明其调度原因。这两次慢翻页前后均为 `cache_evictions=0`，本轮没有测量堆查询持锁区间或强制资源压力，不能借此认定缓存回收热点或原 watchdog 问题已解决。

三轮采集未见崩溃、task watchdog、驱动失败帧、输入溢出或测量命令超时。0.5.1 的 trace 截止完整；最新初轮和复测各有一个书库封面任务跨过截止点，均发生在全部计时正文动作之后。保留 `operations_unfinished`，不发布覆盖所有后台任务的完整耗时分布；上述逐帧配对计时与这个后台任务分开判断。刷写准备另通过正常电源菜单等待实际 active 指标归零，没有把 `count=counting` 当作仍有活动 worker。

## 资源与安装恢复

配对两轮的最低采样内部空闲均为 80,231 B、最大内部块均为 34,816 B、输入任务剩余栈均为 2,640 B。0.5.1／最新的 PSRAM 空闲采样最低值分别为 2,437,068／2,434,976 B，最大连续块为 1,572,864／1,409,024 B，主任务剩余栈为 4,404／6,644 B。这些是离散采样，未覆盖全部瞬时峰值或全部生命周期，不能据此作无泄漏、最坏栈或资源改善保证。

本次重新识别设备，实际双 OTA 槽均为 4 MiB，otadata 两项 CRC 有效且为 VALID，选择 ota_1 `0x410000`。仅更新该活动应用槽；每次写入及独立 verify-flash 通过，前 64 KiB 与 otadata 写前／写后一致，启动核对实际版本、VCOM 与 TF。未改 bootloader、分区、工厂校准或格式化 TF，也未进入 MSC。

大块应用备份及部分 stub 读取发生中断；保留异常，分块并使用已验证的 ROM 读取回退补齐后，应用摘要与测试前 Release 一致。首轮探针还曾把已保存锚点误当作刚呈现位置而中止；原始失败保留，修正为逐帧校验与停留保存后的锚点往返，再执行上述三个完整轮次。两项均没有改生产固件或放宽 watchdog。

结束前通过正常应用路径恢复原书，独立核对保存锚点、修订号、46 px 与正文画布 CRC 与测试前一致，再等待资源交还。随后装回完整备份的原 Release `0.5.1+ga2871cc`，3,949,216 B，SHA-256 `b28fe902b46c12132fc78539fca687e784ba462685991589956c3dd848d9c81e`；独立校验、元数据保持、启动版本、实际槽、VCOM 与 TF 通过。最终 Release 关闭诊断，本轮没有在该最终启动后重新导出画布或逐文件比对 TF；恢复的阅读状态以写入前的诊断核对为证。原创测试样本和三书测试进度保留在专用目录。

原始字节、事件、逐次状态、源码／镜像来源、应用备份、安装与汇总脚本位于忽略目录 `.local/version-perf-20261104/`，摘要清单为 `evidence-sha256.json`。关键命令为既有 EIM 的 `sh tools/build_firmware.sh diagnostic`、本批私有 `install_app.py`／`measure.py`／`prepare_flash.py`、`compare.py`，以及 `tools/summarize_reader_perf.py`；完整参数和失败输出随目录保留。构建初次被沙箱 psutil/sysctl 权限阻止，获准以原入口重跑通过；串口也在获准环境操作。没有替换全局工具链或依赖。交接与差异检查结果在本日开发状态记录。
